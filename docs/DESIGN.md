# 设计与数据所有权

目标是让玩家稳定地拥有、购买和展示称号，让管理员在游戏内管理销售，并能安全地迁移旧服数据。旧插件的数据结构仅作为一次性读取来源；DeerTitle 的模型以这些目标重新设计。

## 成功标准

- 玩家通过原生 Dialog 完成查看、购买、佩戴、自定义与预览，不需要记住编辑格式。
- 同一余额不能被并发花两次，同一份限量库存不能在两个子服上重复售出。
- 新建或修改个人称号只在成功保存时消耗一次自定义次数。
- 源数据保持只读；导入可预览、整批提交、重复执行不重复发放。
- 玩家退出和插件关闭后清理内存中的会话、任务及连接；占位符不阻塞游戏线程。

## 新数据模型

| 表 | 负责的数据 |
| --- | --- |
| `dt_title` | 名称、MiniMessage 显示、描述、创建者、个人/公共属性、启用状态、编辑版本 |
| `dt_player` | UUID、名称、当前称号、内置币、自定义次数、修订计数 |
| `dt_ownership` | 玩家与称号的唯一关系、到期时间 |
| `dt_listing` | 商品价格、货币类型、总库存、已售/预留量、销售时段、发放期限、编辑版本 |
| `dt_payment` | 外部付款订单、金额快照、发放对象、状态、时间 |
| `dt_import_map` | 稳定来源标识与旧记录 ID 到新记录的映射 |
| `dt_mutex` | 跨进程写事务的互斥点 |
| `dt_schema` | 数据结构版本 |

时间以 UTC 时间点存储，UI 时区和来源数据时区在边界转换。金额通过 BigDecimal 验证，保存十进制文本，避免 SQLite 浮点与远端 DECIMAL 规则的差异；币余额使用带溢出检查的整数。

## 一致性与故障

普通读取不持有全局写锁。人类操作触发的变更进入短事务，先获得数据库互斥行，再验证所有权、版本、余额、库存和时间条件；所有数据一起提交或回滚。管理员按“剩余量”编辑库存时，同时验证打开表单时的已售数量，避免并发销售改变输入含义。

Vault 以返回的交易结果为准。内部保留库存预留与单次扣款保护，返回成功后发放，返回失败或异常后取消并释放库存，不要求管理员管理订单状态。后台自动补发已记录成功的购买，并释放超过 5 分钟的中断预留；维护只操作数据库，不再调用 Vault 扣款或退款。这个游戏场景的取舍接受扣款瞬间崩溃或提供者异常可能产生的少量不一致。

## 线程与内存

- JDBC 操作使用有界线程池和任务队列；连接、语句、结果集按作用域关闭。插件退出关闭连接池，并仅清理自身类加载器拥有的 JDBC 注册和 MySQL 清理线程。
- 玩家展示、Dialog 及 Vault 操作通过玩家实体调度器执行，支持 Folia。控制台消息通过全局调度器发送。
- 每个在线 UUID 只有一个原子 Session，包含连接代数、当前快照和刷新状态。退出移除整个 Session；旧连接或旧查询不能重新插入数据。
- 文字渲染结果随快照预计算，PlaceholderAPI 只返回已有字符串；缓存超时或称号过期时停止展示。缓存不保存 Player、World 或 Inventory。
- Dialog 页面令牌单次有效、绑定玩家、短期过期；输入和权限在服务端重新检查。失败页和异步成功均验证当前页面，旧回调不能覆盖新页面。
- 导入最多保留一个有期限、绑定管理员的预览；源读取有行数与文本预算，退出、关闭或新预览使旧结果失效。

## 迁移边界

旧币余额、日期、库存的实际含义在读取阶段解释；旧外部经济余额不复制。旧记录中不存在的数据不会凭描述补造，例如个人编辑权限和剩余自定义次数。来源映射与目标写入属于同一个事务，导入任务不调用 MiniPlayerTitle 初始化或旧数据升级逻辑。
