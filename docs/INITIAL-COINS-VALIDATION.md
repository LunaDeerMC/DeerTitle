# 1.0.2 初始称号币与导入验证

日期：2026-10-28。默认 `economy.initial-coins: 0` 保持升级行为；要延续旧服首次赠送 100 称号币的规则，配置为 `100`。

## 账户创建与迁移

初始余额和玩家行在同一个数据库写事务中创建，复用跨服互斥行；登录回调不另行加币。所有会修改余额、次数或称号权益的业务操作递增玩家 `revision`，改名不影响它。`revision == 0` 表示尚未发生业务变动，因此导入可以用旧余额替换未使用的初始化余额；已有业务变动的账户继续按原有规则合并余额。

新迁移账户直接以零初始化后导入旧余额，不领取初始币。以后登录、修改赠币配置或重复导入均不再发放。Vault 模式传给存储层的有效初始币为零，不调用外部经济接口发放余额。无需修改已有数据库结构。

## 自动化验证

`./gradlew --offline --no-daemon -PreleaseVersion=1.0.2 clean build` 通过：**90 项通过，0 失败，22 项外部数据库测试按环境条件跳过**。

另外在独立的本地 PostgreSQL 和 MySQL 数据库各执行全部 **22 项** 存储契约测试，均通过且没有跳过。新增场景包括：

- 两个独立连接池同时提交 24 次同 UUID 创建请求，只得到一次初始余额。
- 重复登录、改名、配置从 100 调到 200，不改变已有余额；新账户使用新配置。
- 管理员先操作离线玩家，也只初始化一次。
- 启用初始币时迁入旧余额 37 或 0，最终仍分别是 37 或 0。
- 先初始化 100、再将配置改为 200，未经业务操作的账户迁入 37 后仍是 37。
- 已发生业务变动的账户保留原生余额，重复导入不重复加币。
- 配置缺项默认为零；负数、小数、超上限、整数溢出、非数字均被拒绝。
- Vault 模式保留配置值但有效初始币为零。

## 旧颜色语法

1.0.1 将整个未知 `<...>` 片段转义，导致字面尖括号内的 `&#RRGGBB` 显示为文字。1.0.2 只转义标签界定符，继续解析其中的旧颜色代码。测试覆盖文字、逐字 RGB、装饰及未知点击标签不能获得执行行为。

另使用只读的旧库副本调用真实构建中的导入器和存储层：启用初始币 100，完整导入及重复导入后逐字段核对余额、称号、拥有关系、期限与商品；源文件 SHA-256 不变。逐字比较 MiniPlayerTitle 4.7.0 实际 `ColorParser` 与导入后的输出，全部称号的文字、RGB 和装饰一致，不再需要迁移后单独修改目标记录。私有数据和原始报告不纳入仓库。

## 实际服务端验证

Full 与 Lite 各在独立新建的 Folia 26.1.2 build 8 世界执行首次启动及重启，共四次，全部正常加载 1.0.2 并退出。每次通过真实控制台执行导入预览及确认；合成旧账户余额始终为 37，新 UUID 经管理员首次授予称号初始化为 100，重复授予和重启后再次授予仍为 100。SQLite 完整性检查通过，没有插件或依赖解析错误。

Lite 使用已有的 Paper 原生库缓存，本轮缓存新增和改写均为零；冷下载与驱动生命周期覆盖范围见 [1.0.1 验证](FULL-LITE-VALIDATION.md)。本轮不重复完整 UI 或冷下载矩阵。所有测试 JVM、端口和隔离数据库容器已关闭。
